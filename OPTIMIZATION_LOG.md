# Optimization log

## Analyzer media settings

Selected 768 px maximum image edge, up to three evenly spaced carousel images, and a 1024-token per-post output cap. This keeps several visual samples for carousels while materially reducing request payload.

The five-post benchmark compared 25 requests across five settings. At 768 px with three media samples, aggregate input tokens fell 57.3%, encoded image payload fell 58%, measured request wall time fell 41.8%, and estimated cost fell 43.3% versus the 1280 px baseline. Estimated cost was about $0.000973 for that five-post scenario. This is a small sample, so timing is directional and analysis quality was not formally scored. The 512-token output cap did not show a dependable speed improvement and saved little estimated cost; the default remains 1024.

Detailed measurements are in [the benchmark report](exports/instagram-yaroslav_kazo-20261021-220341/optimization_benchmark_20261021T205220Z.md).

## Scraper media concurrency

Added bounded processing across posts: four download workers by default, configurable from one to six with `IG_MEDIA_DOWNLOAD_WORKERS`. The returned manifest retains profile order. Video compression runs under a separate two-job limit so parallel downloads do not start an unbounded number of FFmpeg encodes.

The local unit test uses artificial download delays to verify stable output order and enforce the worker ceiling. It measures concurrency correctness, not Instagram throughput. A real profile rerun is needed before claiming a wall-time improvement because CDN throttling, network conditions, and video mix affect the result.

## Community Cloud CPU throttling — 2026-10-24

- The hosting notice explicitly reported a temporary CPU reduction. Streamlit documents that Community Cloud apps can be throttled when resource limits are met/exceeded: https://docs.streamlit.io/deploy/streamlit-community-cloud/manage-your-app#app-resources-and-limits . No cloud CPU metrics were available to attribute the exact event; full-video transcoding was a confirmed expensive operation in this implementation, not a measured sole cause.
- Added default-on `APP_LOW_CPU_MODE` for web jobs. It disables full archive-video transcoding, retains the selected source video, caps download workers at two, and uses one FFmpeg thread and one concurrent media-preparation slot. The analyzer still extracts one video frame, uses the same image settings and material limits, and runs model API requests independently in parallel. Source videos can consume more disk space than compressed archives. CLI users retain optional video compression and can configure FFmpeg/preparation concurrency separately.
- FFmpeg decoder/encoder thread counts are explicit and bounded; filter threading is capped at one. Normal reports record the preparation concurrency and web low-CPU flag. Existing active throttling is controlled by the host and is not removed by this change. No percentage or full-profile timing improvement is claimed without a cloud measurement.
- Fixed a confirmed budget-counter bug found during the resource review: the disk-scan loop reused the budget-file path variable, which could redirect the counter write to an export file. Budget writes now always target `budget.json`; a regression case proves export bytes remain intact and the daily limit is enforced.
- Validation: all 42 local tests passed in 2.726 seconds. Coverage includes unchanged selected video bytes when transcoding is disabled, one-at-a-time media preparation with overlapping model requests, CPU-setting bounds, defaults over older settings, and budget-file integrity. A real FFmpeg smoke check on a one-second synthetic video completed: archive compression 20,378 → 5,137 bytes, valid 256×144 JPEG frame (3,844 bytes), with one thread. This validates command compatibility, not cloud CPU reduction.
- Two read-only local Instagram feed checks (with/without a proposed browser media filter) both failed to capture the feed response. No model calls or media downloads were made. The browser-filter change was removed rather than enabled without a successful feed check; the scraping request behavior is unchanged by this release. Local session/feed availability remains unverified, and neither test establishes behavior on the cloud IP.
